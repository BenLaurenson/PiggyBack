# Wise Business API integration

PiggyBack ingests Business profile transactions from Wise into the
`business_*` tables. This directory documents the integration surface.

## Files

- `endpoints.md` — verified endpoint paths, pagination shape, and the
  `getStatement` vs `getActivity` decision. Pre-implementation research
  output, augmented with live-API verification notes.
- `TASK6-BRIEF.md` — distilled brief from live-API verification used as
  the source of truth for `src/lib/wise-api.ts` paths and shapes.
- `response-samples/` — redacted raw JSON responses from live API calls.
  Real production-account data with PII stripped (names, IBANs, account
  numbers, descriptions). Preserves structural shapes for reference.

## Authentication

Personal API token. Generated by the user in their Wise Business account
under Settings → API tokens. Stored encrypted in
`business_wise_configs.encrypted_token` via the existing AES-256-GCM
helper in `src/lib/token-encryption.ts`. Decrypted on demand.

## Environments

- Live: `https://api.wise.com`
- Sandbox: `https://api.sandbox.transferwise.tech`

Selected per-user via `business_wise_configs.wise_environment`.

## Pagination

Wise's statement endpoint does NOT paginate via cursor — verified live.
The sync worker (Plan 1A.2) chunks history into date windows (max 469
days per call per Wise's documented limit) and concatenates results.
`MAX_PAGES = 500` safety cap in `src/lib/wise-api.ts` is a defensive
guard for any future cursor-paginated endpoint.

## referenceNumber is NOT a unique key

Verified empirically: Wise's `referenceNumber` repeats across:

- Refund pairs (DEBIT charge + CREDIT refund on the same balance share
  the reference).
- FX legs (one CONVERSION emits two rows — debit on the source-currency
  balance + credit on the target-currency balance — sharing the
  reference).

The `business_transactions` schema therefore stores `reference_number`
(raw Wise value, used for display/audit) separately from
`wise_transaction_id` (the per-leg idempotency key composed by
`processWiseTransaction` as `${reference_number}|${direction}`).

The unique index on `(user_id, wise_transaction_id)` is safe because
the composite key incorporates direction.

## Phase 1A subset

The Phase 1A `WiseApiClient` (`src/lib/wise-api.ts`) covers:

- `ping()` — `GET /v1/me` for token validation.
- `getProfiles()` — `GET /v2/profiles`. The connection flow filters to
  the business profile by `type === 'BUSINESS'` (uppercase, verified).
- `getBalances(profileId)` — `GET /v4/profiles/{profileId}/balances?types=STANDARD`.
  One row per currency balance.
- `getStatementPage(...)` — `GET /v1/profiles/{profileId}/balance-statements/{balanceId}/statement.json`
  with `currency`, `intervalStart`, `intervalEnd`, `type=FLAT`.

## Phase 1B (not yet implemented)

- `registerWebhook(profileId, payload)` / `deleteWebhook(...)` — Wise
  Subscriptions API.
- Webhook signature verification — Wise signs payloads with **RSA-SHA256**
  (newer subscriptions: RSA-SHA512). The shared HMAC pattern used by the
  Up Bank webhook (`src/app/api/upbank/webhook/route.ts`) is wrong for
  Wise; do not reuse that code path.
- Public keys: env vars `WISE_PUBLIC_KEY_LIVE` and `WISE_PUBLIC_KEY_SANDBOX`
  (PEM strings). Declared in `src/lib/env.ts` at Phase 1A.
